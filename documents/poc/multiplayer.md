## LANで残る受入

オーナーの方針に従い、マルチプレイの接続をコードに実装し、自動検査を先に通す。実際のLANの検証は後日、友人とのプレイ時に行う。現在は独立した二端末からの実ゲーム記録を取得しておらず、自動検査の成功を実LANの成功とは表示しない。接続先や仮想環境を調べた際の権限拒否は、2台目が存在しない証明にはならない。

| 段階 | 必要な証拠 | 現在 |
|---|---|---|
| 二端末の準備 | 各端末への操作経路、Civ6 1.0.12.68とGathering Storm、同じソース・MOD、各端末自身の採取CLI。2本のゲームを動かせる利用権 | 後日の友人とのプレイで確認 |
| 実接続と初期採取 | 同一ゲームのLAN接続、ホストと参加側の別々の原ログ・ゲーム設定・時点、各人2件の成長記録 | 未実証 |
| 自然な手番と成長 | 双方が同じ採取段階で待機した証拠、所有者とUnit IDをキーに4件の全値一致、元の成長処理に対する加算回数 | 未実証 |
| 途中保存と再開 | 新しい実保存ファイルと保存完了、双方の再開ログ、保存前と再開後の4件全値一致、再開による経験値の重複加算なし | 未実証 |
| 切断と再参加 | 参加側の切断・再参加とホスト側の対応する原ログ、同じゲーム・手番・段階へ戻った記録、再参加前後の全値一致と重複加算なし | 未実証 |

実機は標準 `live_chain` の共有枠で使い、待ちがあれば30分の規則に従う。元のホットシートを再実行する予約は作らない。LANでは、双方の手番の設定を記録し、ゲームの手番が動かない採取段階を実際に確認してから一度ずつ照会する。同一ターンの復元前後を比較する場合は、保存前の対象プレイヤーの成長処理が完了したことと加算済みターンを記録し、再開後に新しい手番へ進めず採取する。各端末で一回の読取中にターンや手番が変わらなかったことだけでは、二端末が共通の段階にいたとは判定しない。

`civ6-growth-sync capture` は各端末自身のループバックFireTunerへ一回だけ接続する。人間0・1の二人だけが生存する主要文明で、各人に成長記録が2件あるゲームが対象。AI20人を含む日本22枠のLANゲームは現在の採取対象外。ホットシートの採取値、同一端末から複製した値、模擬通信を実LANの証拠へ使わない。

```powershell
# ホスト側で実行。各ラベルは実際の今回のゲーム・採取段階に合わせる。
civ6-growth-sync capture --endpoint host --session <今回のゲーム> --barrier <今回の境界> --phase <採取段階> > host.json
# 別端末の参加側で実行。同じ採取段階の原ログも別々に保存する。
civ6-growth-sync capture --endpoint guest --session <今回のゲーム> --barrier <今回の境界> --phase <採取段階> > guest.json
civ6-growth-sync compare host.json guest.json
```

比較成功が示すのは、渡された同じ段階の二記録の一致までである。端末名やラベルは呼出し側の申告なので、原ログと接続記録を併せて判定する。各段階のJSONは書き換えず保持する。保存前後・再参加前後は `civ6-growth-sync compare-restoration <前ホスト> <前参加側> <後ホスト> <後参加側>` で比較する。前後の段階は異なるラベルを要求し、それぞれの段階で二端末の一致を確認した後、同じゲーム・端末・操作プレイヤー・ターンであることと全4件の全値保持を検査する。両端末で同じ重複経験値が増えた場合も不合格になる。段階ラベルをそろえて元JSONを書き換えない。このコマンドも、実際に保存読込や再参加したこと自体の証明にはならない。

成長処理は [GrowthUI本体](../../poc/JAC_PoC_GrowthUI/Scripts/JAC_PoC_GrowthUI_Gameplay.lua) の手番開始と `LastXPTurn` に照合する。手番が増えた段階で常に全値不変を要求するのではなく、通常の成長に一致するかを確認する。保存読込や再参加自体で、同じ加算済みターンの経験値が増えていないことを別に確認する。

コード検査はRustの `growth_multiplayer.rs` で、配布するGameplay Luaを独立したLua 5.1環境に読み込む。操作プレイヤーとプレイヤー・ユニットの列挙順を変え、重複した手番開始、二度の保存状態のJSON化と新しい環境への復元、同じターンでの再参加、次ターンの成長、レベル上限と全メタデータの保持を確認する。一人の開始ユニットだけが未到着の場合に初期化を終える旧不具合は、修正前に失敗した検査で再現した。ネットワーク対戦では、設定上の人間枠がGameplayの名簿へ到着したことを確認し、全員の開始ユニットがそろうまで記録を保存しない。初期化するのはGameplayの手番開始だけで、各端末の読込画面の閉鎖では状態を書かない。UI専用の読込イベントがなくても手番処理を登録する。逆側の到着遅れ・ユニットを持たないAI・名簿到着遅れ・読込時刻差、ネットワーク設定での保存復元を検査する。これはゲームエンジンの配送順を実測した結果ではなく、その順序が変わった場合のコード検査である。

設定の人間一覧と観戦者一覧は画面側だけで読み、Rustから生成する空のUIコンテキストが公式 `EXECUTE_SCRIPT` で送る。Gameplayから画面専用の参加者一覧APIを呼ばない。受信側はエンジンが渡す要求者、現在の手番、主要文明のID、順序・重複・欠落を検査し、受理した一覧を保存する。初期化前に届いた手番開始も保存し、初期化後にターン・所有者順で一度だけ加算する。待機中の保存から新しい環境へ戻った場合も最初の人間の経験値を取りこぼさない。画面が送った実際の要求を独立した二つのGameplay環境へ渡す検査と、画面の登録・Rust生成物・CLI出力の一致を検査する。

初期化前に人間枠がAIへ切り替わった場合は、活動中の人間が更新した設定一覧を同期要求で届ける。Gameplayの人間が全員含まれることを確認し、人間の欠落を拒否する。待機中の手番記録は生存主要文明ごとに実際の開始回数と最後のターンへまとめ、適用時に人間だけへ加算する。人間への切替が遅れても手番を失わず、長い待ちによる保存量の増加を抑える。旧形式の保存記録も読み込む。途中のユニット書込み失敗で残った待機記録は、次の手番で通常の成長より先に再処理する。同じ画面要求の未受理時は、ターン・実行者・一覧ごとに8回で再送を止めて診断し、次ターンまたは一覧変更で再試行する。

APIの文脈は本体StagingRoomと、作者の[GameConfiguration実測一覧](https://github.com/Sukritact/Civilization-VI-Modding-Knowledge-Base/blob/master/Objects/GameConfiguration/GameConfiguration.md)を照合した。人間枠の読み取りはUI、ネットワーク判定はScriptとUIの双方で利用される。手番の再確認には[Playerの実測一覧](https://github.com/Sukritact/Civilization-VI-Modding-Knowledge-Base/blob/master/Objects/Player/Player.md)のScript・UI共通の `IsTurnActive` を使う。実エンジンの配送・表示・保存の確認は後日のプレイへ残す。

同盟と家名には `clans_alliance_multiplayer.rs` の13検査を追加した。家名の状態変更は公式Gameplayのターンイベントで行い、存在しない同盟要求者を拒否する。独立した二環境で要求順・二重要求・所有者変更・保存再構成を照合する。ホットシートで同じ申し込み元から別の人間へ操作が移った場合も、申し込みを表示する。

宗教は8分岐と本人の英雄操作を同期要求へ接続し、MODのマルチプレイ対応を有効にした。英雄の加入先・クラス・寿命を画面側で読み、本人が送った観測を保存予約・実ユニットの所有者と種類に照合する。画面由来の加入先・寿命をGameplayが独立して確認した証拠とは扱わず、その限界も保存する。詳しい対応範囲とAIの合法代替は [宗教の記録](religion-persistence.md)を参照する。

作品移管は、人間の操作担当を保存し、原作品の移動元と移動先を一時的にその人間へ借りる経路を追加した。人間の吸収先は本人を操作担当とする。AIの吸収先では、生存する人間のうち最小のIDを持つ人を担当とし、その人の手番を待つ。操作担当と最終受取人は別々に保存する。各Gameplay環境は同じ受信記録から借用・移動・返還を進める。局所的な画面キャッシュから各端末が別々に進行を決めない。二都市の状態、原作品の唯一性、所有者・座標・スロット、要求の段階・番号と保存後の再送を照合する。観測する小数値は17桁で送って数値の往復を保持する。

散逸と回収も二都市の同期手順へ接続する。散逸先の自由都市と、人間の操作担当を区別する。回収では、取引とは別の回収予約へ段階・要求番号・原作品の来歴・最終枠を保存する。要求を受けたときは両方の予約集合を検索し、重複したトークン、同じ都市の同時借用、同じ作品indexの競合を拒否する。世界報酬は保存された受取人へ渡し、操作担当へ置き換えない。保存後にUIの送信結果が分からなくなった場合は、元の要求を再発行せず、移動済みの観測または明示的な拒否を待つ。

作品移管のコード対応は条件付きである。借用される首都・最後の都市、Palaceの作品、空の博物館へ移せないArtifactは有効にしていない。拒否は都市を変える前に行う。人間の操作担当がいない場合は副作用を発行せず待機する。これら未対応条件まで完了したとは表示しない。元ToDo996はこの残りを保持する。散逸・回収・AI受取先の追加候補は検査・別モデルの追審・CI・マージの完了を別途記録する。

誓約には `oaths_multiplayer.rs` の4検査を追加した。既存のGameplay要求受信処理を二環境で実行し、要求本文のプレイヤー番号ではなくエンジンが渡した要求者を使うこと、異なる家の誓約・古い期・不正件数を拒否すること、保存後の二重要求で選択や記録を上書きしないことを照合する。全66効果の実数量を確認するToDo134の代替とはしない。
