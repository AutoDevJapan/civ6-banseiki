## LANで残る受入

オーナーの方針に従い、マルチプレイの接続をコードに実装し、自動検査を先に通す。実際のLANの検証は後日、友人とのプレイ時に行う。現在は独立した二端末からの実ゲーム記録を取得しておらず、自動検査の成功を実LANの成功とは表示しない。接続先や仮想環境を調べた際の権限拒否は、2台目が存在しない証明にはならない。

| 段階 | 必要な証拠 | 現在 |
|---|---|---|
| 二端末の準備 | 各端末への操作経路、Civ6 1.0.12.68とGathering Storm、同じソース・MOD、各端末自身の採取CLI。2本のゲームを動かせる利用権 | 後日の友人とのプレイで確認 |
| 実接続と初期採取 | 同一ゲームのLAN接続、ホストと参加側の別々の原ログ・ゲーム設定・時点、各人2件の成長記録 | 未実証 |
| 自然な手番と成長 | 双方が同じ採取段階で待機した証拠、所有者とUnit IDをキーに4件の全値一致、元の成長処理に対する加算回数 | 未実証 |
| 途中保存と再開 | 新しい実保存ファイルと保存完了、双方の再開ログ、保存前と再開後の4件全値一致、再開による経験値の重複加算なし | 未実証 |
| 切断と再参加 | 参加側の切断・再参加とホスト側の対応する原ログ、同じゲーム・手番・段階へ戻った記録、再参加前後の全値一致と重複加算なし | 未実証 |

実機は標準 `live_chain` の共有枠で使い、待ちがあれば30分の規則に従う。元のホットシートを再実行する予約は作らない。LANでは、双方の手番の設定を記録し、ゲームの手番が動かない採取段階を実際に確認してから一度ずつ照会する。同一ターンの復元前後を比較する場合は、保存前の対象プレイヤーの成長処理が完了したことと加算済みターンを記録し、再開後に新しい手番へ進めず採取する。各端末で一回の読取中にターンや手番が変わらなかったことだけでは、二端末が共通の段階にいたとは判定しない。

`civ6-growth-sync capture` は各端末自身のループバックFireTunerへ一回だけ接続する。人間0・1の二人だけが生存する主要文明で、各人に成長記録が2件あるゲームが対象。AI20人を含む日本22枠のLANゲームは現在の採取対象外。ホットシートの採取値、同一端末から複製した値、模擬通信を実LANの証拠へ使わない。

```powershell
# ホスト側で実行。各ラベルは実際の今回のゲーム・採取段階に合わせる。
civ6-growth-sync capture --endpoint host --session <今回のゲーム> --barrier <今回の境界> --phase <採取段階> > host.json
# 別端末の参加側で実行。同じ採取段階の原ログも別々に保存する。
civ6-growth-sync capture --endpoint guest --session <今回のゲーム> --barrier <今回の境界> --phase <採取段階> > guest.json
civ6-growth-sync compare host.json guest.json
```

比較成功が示すのは、渡された同じ段階の二記録の一致までである。端末名やラベルは呼出し側の申告なので、原ログと接続記録を併せて判定する。各段階のJSONは書き換えず保持する。保存前後・再参加前後は `civ6-growth-sync compare-restoration <前ホスト> <前参加側> <後ホスト> <後参加側>` で比較する。前後の段階は異なるラベルを要求し、それぞれの段階で二端末の一致を確認した後、同じゲーム・端末・操作プレイヤー・ターンであることと全4件の全値保持を検査する。両端末で同じ重複経験値が増えた場合も不合格になる。段階ラベルをそろえて元JSONを書き換えない。このコマンドも、実際に保存読込や再参加したこと自体の証明にはならない。

成長処理は [GrowthUI本体](../../poc/JAC_PoC_GrowthUI/Scripts/JAC_PoC_GrowthUI_Gameplay.lua) の手番開始と `LastXPTurn` に照合する。手番が増えた段階で常に全値不変を要求するのではなく、通常の成長に一致するかを確認する。保存読込や再参加自体で、同じ加算済みターンの経験値が増えていないことを別に確認する。

コード検査はRustの `growth_multiplayer.rs` で、配布するGameplay Luaを独立したLua 5.1環境に読み込む。操作プレイヤーとプレイヤー・ユニットの列挙順を変え、重複した手番開始、二度の保存状態のJSON化と新しい環境への復元、同じターンでの再参加、次ターンの成長、レベル上限と全メタデータの保持を確認する。一人の開始ユニットだけが未到着の場合に初期化を終える旧不具合は、修正前に失敗した検査で再現した。ネットワーク対戦では、設定上の人間枠がGameplayの名簿へ到着したことを確認し、全員の開始ユニットがそろうまで記録を保存しない。初期化するのはGameplayの手番開始だけで、各端末の読込画面の閉鎖では状態を書かない。UI専用の読込イベントがなくても手番処理を登録する。8検査が成功し、逆側の到着遅れ・ユニットを持たないAI・名簿到着遅れ・読込時刻差を含む。これはゲームエンジンの配送順を実測した結果ではなく、その順序が変わった場合のコード検査である。

同盟と家名には `clans_alliance_multiplayer.rs` の13検査を追加した。家名の状態変更は公式Gameplayのターンイベントで行い、存在しない同盟要求者を拒否する。独立した二環境で要求順・二重要求・所有者変更・保存再構成を照合する。ホットシートで同じ申し込み元から別の人間へ操作が移った場合も、申し込みを表示する。

誓約には `oaths_multiplayer.rs` の4検査を追加した。既存のGameplay要求受信処理を二環境で実行し、要求本文のプレイヤー番号ではなくエンジンが渡した要求者を使うこと、異なる家の誓約・古い期・不正件数を拒否すること、保存後の二重要求で選択や記録を上書きしないことを照合する。全66効果の実数量を確認するToDo134の代替とはしない。
