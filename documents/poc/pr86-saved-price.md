# 加入時の進化費用と価格更新

加入済み人物の進化費用は、加入時の価格契約から読みます。現在の初期データ価格は新規加入に使います。根拠は [SSOT 9.4 の指導者の進化](../spec/ssot/09-assimilation-religion.md) の「初期費用は加入時に保存し、以後の性格変更や初期データの調整では変えない」です。仕様の変更はありません。

## 保存と照合

- 通常の Gameplay 保存記録に、人物ごとの加入時価格を `prices` として保存します。人物ID、加入先と加入元、偉人と総督の型・番号・Hash、基礎昇進の型、加入時の catalog binding を一緒に記録します。契約の金額自体も加入時の binding と照合します。
- 準備時の `EVOLUTION_COST` と `EVOLUTION_SURCHARGE` は、この独立した価格契約と一致する必要があります。欠損、型の違い、範囲外、金額を減らした準備記録を現在価格から補いません。
- d21 の保存には価格契約がありません。当時の初期化で保存した catalog binding 全文を再構成し、そこに含まれる元価格を使います。価格だけが変わった場合は読めます。元価格を超える分の正規の支払専用昇進を追加することもできます。既存の人物・総督・偉人・昇進の番号、Hash、型、所属の変更や binding 破損は拒否します。
- 次の人物が加入するとき、既存人物の契約も元の binding と準備記録を照合してから取り込みます。過去の支払通知、確定済み消費、予約、binding は書き換えません。

## 支払いと資格

進化完了、通常の支払記録、称号予約、任命資格、配置資格の通知、UI の支払順序は同じ保存価格を使います。本体へ渡す catalog の価格と昇進の列も保存価格に合わせます。別所有者や別人物の支払通知は代用できません。

価格式と支払専用昇進の定義を分離しています。Rust が生成する SQL は、d21 の22人の支払昇進を元の登録順で作り、残りの昇進を後ろへ追加します。価格を下げても元の型・番号・Hash・所属が消えません。全員に費用1〜3を支払える効果なしの昇進2段階を固定しておき、実際に使う先頭の段階数は人物の加入時価格で決めます。価格パラメーターからDBを再構築しても、この定義と所属は変わりません。過去の支出や昇進取得を再送して移行する処理はありません。

一人の準備金額が破損しても、独立した価格定義は失われません。破損した人物の資格を閉じ、別所有者の正常な人物は再照合を続けます。称号の消費確認、昇進の取得通知、順序、部分支払、二重送信の保護は継続します。

## 生成と回帰検査

Rust の生成元は `civ6-persona-events-rs/src/normal.rs`・`price_routes.rs` と、`civ6-native-bridge-rs/src/persona_finalization.rs`・`paid_glue.rs` です。Gameplay・共有規則・UI の Lua を生成します。支払定義の SQL は `civ6-data-rs/src/persona_payments.rs` から生成します。生成 CLI の出力先は明示した作業フォルダです。

`persona_sql_price.rs` は旧d21 SQLと価格パラメーターから別々にDBを構築します。d21型の保存、契約がある旧定義の保存、新定義での価格契約付き保存を、費用1・2・3の上昇・下降と支払0・部分・完了で照合する54条件です。前候補では `rebuilt SQL closed the saved catalog` で失敗しました。実SQLを使い、別所有者・異人物・未知通知・破損通知も拒否します。DB検査は価格式の再計算後もd21の昇進番号・Hashを保持し、全員の定義・所属・前提・効果なしが一定であることを確認します。

`saved_price_cases.rs` は、初期データ更新前の保存を別の Lua 5.1 実行環境へ移し、価格1・2・3の上昇・下降、未払い・部分支払・既進化、元の資格、予約、支払通知、新規加入価格を検査します。元のコードでは `saved_price_survives_price_only_reload_with_partial_and_completed_payments` が通常支払記録を読めずに失敗します。金額・契約・所有者・人物の破損、元の公式昇進が欠ける場合も検査します。

`persona_finalization.rs` は、出荷 UI と本体操作を模す既存の実行キューを使います。読込後に元の未払い昇進だけを取得し、再請求と早期の偉人除去を防ぐ検査です。保存済み功績と技能、配置後の功績獲得も対象です。既存の receipt 破損検査は、本来防いでいた早期除去と別所有者への影響を引き続き検出します。

## 受入の境界

レビューSuggestionのAI費用2・3固定は、`ai-operation-audit.rs` の非公開診断モジュール `Replay` にあります。公開d6c20082も含め、呼出しは独立検査だけで、実行許可や支払送信のAPIはありません。gatewayはこのモジュールの `Epoch` 型だけを使い、`Replay` を製品経路へ接続していません。この限定診断の固定条件は変更しません。通常の本体用catalogは人物の加入時価格を使います。

これらは Rust と Lua 5.1 の回帰検査です。実ゲームを起動する担当の受入には加算しません。通常の自動起動・読込、AI 本人の費用2・3の支払い、途中保存を含む MP、中和による効果と功績の停止・回復は親 ToDo880 の未達のままです。通常製品経路の leaderperson-163 は GP 加入と最初の保存読込が成功し、25/114 手順の後に総督待機で失敗しています。
