# 加入時の進化費用と現行版の保存

加入済み人物の進化費用は、加入時の価格契約から読みます。現在の初期データ価格は新規加入に使います。根拠は [SSOT 9.4 の指導者の進化](../spec/ssot/09-assimilation-religion.md) です。公開前の開発版にはプレイヤーの旧セーブがないため、旧版の型・番号や価格変更をまたぐ互換性を保証しません。同じ現行版の途中支払いと保存・読込は検証対象のままです。

## 保存と照合

- 通常の Gameplay 保存記録に、人物ごとの加入時価格を `prices` として保存します。人物ID、加入先と加入元、偉人と総督の型・番号・Hash、基礎昇進の型、加入時の catalog binding を一緒に記録します。契約の金額自体も加入時の binding と照合します。
- 準備時の `EVOLUTION_COST` と `EVOLUTION_SURCHARGE` は、この独立した価格契約と一致する必要があります。欠損、型の違い、範囲外、金額を減らした準備記録を現在価格から補いません。
- 保存された契約は、その現行版の人物・総督・偉人・昇進の定義と照合します。定義が欠ける、別人物を指す、契約が壊れている場合は、現在価格で補修せず処理を拒否します。旧版からの移行を製品の受入条件にはしません。
- 次の人物が加入するとき、既存人物の契約も元の binding と準備記録を照合してから取り込みます。過去の支払通知、確定済み消費、予約、binding は書き換えません。

## 支払いと資格

### 加入の取引

加入前に、保存台帳・加入元・既存の価格契約を検証して、変更前と変更後の価格記録を準備します。準備中は保存値を変更しません。通常の本体読取りによる過去支出の確定を済ませてから準備し、新しい偉人の生成より前に記録可能性を確かめます。壊れた旧台帳や金額を現在価格で修復して加入を進めません。

生成後は同じ検証条件を再確認し、価格記録・加入台帳・実物の人物IDをそろえて確定します。生成、価格記録、加入フィールドの書込みに失敗した場合、今回変更した保存値を戻し、今回生成した個体だけを公式の `GetUnits():Destroy` で除去して不在を確認します。公式 `DLC/CivRoyaleScenario/Scripts/CivRoyaleScenario_UnitCommands.lua:392` もこのAPIを使用しています。加入前からいた個体は除去も改名もせず、同じIDで採用します。API呼出しと人物の不在はLua 5.1の本体操作fixtureで検査しており、実ゲームでの削除成功を主張するものではありません。

処理中だけ `JOIN_TRANSACTION` に取引の対象と巻戻し内容を保存します。削除や保存の復元が拒否されたときは完了にせず、その記録で対象を追跡します。再送は以前の取引の巻戻しだけを行い、二体目を生成しません。無関係な支出・通知・加入元の保存値へ巻戻す権限はありません。正常な確定と完全な巻戻しの後はこの記録を消します。

復元前後の価格台帳も同じ金額・binding・人物・所有者の検証へ通します。既存の価格契約を別の金額へ戻す記録は拒否します。旧保存からの取込みを戻す場合も、元のbindingと加入時費用を変えない取込みだけを対象にします。復元用記録の別人物の金額が破損した負例では、その人物の契約と偉人を保持し、再送しても生成を増やさないことを検査します。

`persona_join_transaction.rs` は出荷Joinと本体操作を模す既存の実行キューで、不正台帳、加入元不一致、生成後の価格記録拒否、書込み拒否と例外、再入、削除拒否後の再送、既存人物のID・名前の保持を検査します。共有targetで以前のworktreeへ焼き込まれた検査支援ライブラリが再利用されても、Cargo検査の実行中の作業フォルダからMODを読むようにし、検査対象が今回のフォルダと一致することを確認します。

進化完了、通常の支払記録、称号予約、任命資格、配置資格の通知、UI の支払順序は同じ保存価格を使います。本体へ渡す catalog の価格と昇進の列も保存価格に合わせます。別所有者や別人物の支払通知は代用できません。

Rust が生成する SQL は、現在の人物別費用から必要な効果なしの公式昇進だけを登録します。費用1は基礎のみ、費用2は追加1段階、費用3は追加2段階です。価格パラメーターからDBを作り直した場合も、その価格に必要な定義と所属だけを作ります。旧版のために余分な昇進を残さず、過去の支出や昇進取得を再送して移行する処理も追加しません。

一人の準備金額が破損しても、独立した価格定義は失われません。破損した人物の資格を閉じ、別所有者の正常な人物は再照合を続けます。称号の消費確認、昇進の取得通知、順序、部分支払、二重送信の保護は継続します。

## 生成と回帰検査

Rust の生成元は `civ6-persona-events-rs/src/normal.rs`・`price_routes.rs`・`join_transaction.rs` と、`civ6-native-bridge-rs/src/persona_finalization.rs`・`paid_glue.rs` です。Gameplay・共有規則・UI の Lua を生成します。支払定義の SQL は `civ6-data-rs/src/persona_payments.rs` から生成します。生成 CLI の出力先は明示した作業フォルダです。

`persona_sql_price.rs` は現在SQLと価格1・2・3の各設定からDBを構築します。各DBと同じ定義で、未払い・部分支払い・全額支払いを別のLua実行環境へ保存・復元し、残額、人物、技能、本人会計、配置資格と再送なしを照合します。別所有者・異人物・未知通知・破損通知は拒否します。旧版をまたぐ54条件の過去結果は原記録に保持し、現行版の合格数へ加算しません。

`saved_price_cases.rs` の既存モデル検査は、保存された価格、未払い・部分支払・既進化、資格、予約、支払通知を別の Lua 5.1 実行環境で照合します。価格変更をまたぐモデルの成功は、旧版SQLとの互換性の保証には使いません。旧候補の `saved_price_survives_price_only_reload_with_partial_and_completed_payments` の失敗と修復は原記録に保持しています。金額・契約・所有者・人物の破損、元の公式昇進が欠ける場合も検査します。

`persona_finalization.rs` は、出荷 UI と本体操作を模す既存の実行キューを使います。読込後に元の未払い昇進だけを取得し、再請求と早期の偉人除去を防ぐ検査です。保存済み功績と技能、配置後の功績獲得も対象です。既存の receipt 破損検査は、本来防いでいた早期除去と別所有者への影響を引き続き検出します。

## 受入の境界

### 現在費用の支払定義とAIの余分な昇進

公式 `DLC/Expansion1/Data/Expansion1_Governors.xml:77–127,179–229` は昇進の所属と前提を定義します。公式 `DLC/Expansion2/UI/Additions/GovernorPanel.lua:67,365–378,570–576` は `CanPromoteGovernor` と所属一覧を使い、指定昇進の `PROMOTE_GOVERNOR` を送ります。支払い段階を持つ人物では、その所属と基礎前提を定義します。価格1の人物の追加段階は生成しません。

本体用catalogは加入時価格の先頭だけを渡し、出荷人物UIもそれを超える支払いを送りません。現行SQLでは価格1の人物に `TITLE_1` 自体を登録しません。本体の自然な昇進判定にも、本人の次の未払い段階だけを許す制限があります。AIによる正式な候補選択・支払いと通常経路での余分な昇進拒否は、引き続き実機で確認する必要があります。

AIの実際の候補選択と、本体がこの追加昇進を許す条件は未実機です。価格1で基礎だけ取得した人物、価格2で追加1段階だけ取得した人物の両方で、公式称号を残してAI手番と保存読込を観測し、加入時価格を超える候補が本体で拒否されるかを確認する必要があります。`AiPriority` の重み変更を絶対拒否とは扱いません。通常AI費用2・3の実機成功も未実証です。

AI費用2・3を固定した診断は、`ai-operation-audit.rs` の非公開診断モジュール `Replay` にあります。公開d6c20082も含め、呼出しは独立検査だけで、実行許可や支払送信のAPIはありません。gatewayはこのモジュールの `Epoch` 型だけを使い、`Replay` を製品経路へ接続していません。この限定診断の固定条件は変更しません。通常の本体用catalogは人物の加入時価格を使います。

元の `leader-persona-15km.json` は変更していません。費用1の織田確認2箇所の `_TITLE_1` 定義不在という断言をそのまま現在SQLと照合します。旧版互換のため固定2段を登録した候補では両方が失敗し、現在費用に必要な定義だけを生成する修正で成功しました。原失敗は保持し、SQLとLuaの局所成功を元113の実ゲーム通し受入には数えません。原操作・値・順序・断言は削っていません。

これらは Rust と Lua 5.1 の回帰検査です。実ゲームの受入には加算しません。通常の自動起動・読込、AI 本人の費用2・3の支払い、途中保存を含む MP、中和による効果と功績の停止・回復は製品受入条件として未達のままです。通常製品経路の leaderperson-163 は GP 加入と最初の保存読込が成功し、25/114 手順の後に総督待機で失敗しています。

後続の leaderperson-164 も公開e266で25/114手順の後、26番目の総督待機に失敗しました。7個の原artifactと1.19MBの保存は非公開の検証記録に保全されています。原予約や取引を再送せず、未達を保持します。
