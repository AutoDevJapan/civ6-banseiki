# PR86の汎用本体総督枠を判定する短い診断

汎用の本体総督枠を1種追加し、未加入時のAI任命と、未配置時に取得証跡を読めるかを判定する診断を用意した。実機ではまだ実行していない。人物化の完成版ではなく、正本16.1が許可した同等代替の可否を調べる成果である。

正本9.4・4.7は公式称号の会計、公式の都市配置、一都市一人、定着後の都市効果を要求する。純Gameplayの人物状態では公式スパイ中和の対象となる本体総督がない、という先行調査を受けた。人物と枠の対応、および中和との接続は、この診断の後に親担当が実装する。

## 追加したものと費用

万世紀の15km史実地図に限り、テスト専用MOD `poc/JAC_Test_TitleProxy` と、それに依存する `poc/JAC_Test_NativeSlots` を有効にする。前者は元ブランチで人物化MODに直書きされていた比較用の配置不能総督と会計診断を分離したもの。後者は匿名の配置可能枠を加える。診断中だけ前者のSQLが22人物の本体総督登録を取り除く。通常の人物化MODのファイルと484組の任命資格は変更していない。

| 追加物 | 検証すること |
|---|---|
| `Data/JAC_NativeSlots_Probe.sql` | 人物に対応しない配置可能な本体総督1種。忠誠圧力8、遷移強度100、公式の基準定着5ターンを保つ |
| `Scripts/JAC_NativeSlots_GameCore.lua` | 実際のPlayer/Cityプロパティと公式獲得数・使用済み数をGameCoreから読む。診断記録だけをGameCoreで保存し、本体の証跡は書き込まない |
| `UI/JAC_NativeSlots_View.lua` | 公式の任命・配置操作、21AIの早期断言、UI観測の同期送信、定着と保存復元の比較 |
| `leader-persona-native-slots-15km.json` | 主診断44手順。最初のAI手番と未配置時の証跡で早く失敗させる |
| `leader-persona-native-slots-activation-15km.json` | 発効時点の観測33手順。最後に元の未配置時の証跡を再判定し、後から発効しても合格にしない |
| `leader-persona-title-proxy-15km.json` | 分離した支払い候補の診断85手順。社会制度による称号付与をGameplayで行う |

基礎昇進には公式のPlayerプロパティ用modifierとCityプロパティ用modifierを1個ずつ付けた。両方とも量は1。人物名、人物の固有技能、収量効果、任命資格を変える特性、常設の人物との対応は付けていない。通常の忠誠圧力自体がAIに任命価値を与える可能性を、隠さず検査する。

人間には公式社会制度から称号2個、21AIには各3個を与える。人間が比較用の配置不能な支払い総督を任命して1個、その後で通常枠を任命して1個を使う。**通常枠の1個は追加検証の支出**であり、人物の進化費用に算入した完成版の会計ではない。支払いの予約・人物の除去・人物との対応は呼び出さない。

## 最短の実機判定順

実機では比較用MODと匿名枠MODを導入して、主診断を先に実行する。この移植作業ではゲームを起動していない。

1. 加入済み人物がなく、22人物が本体総督候補にもKind登録にも残っていないことを確かめ、公式の称号を付与する。保存処理の完了を待ってから次へ進む。
2. **最初のAI手番の直後**に21AIを調べる。全AIが3個以上の使用可能な称号を保ち、未対応の通常枠・支払い総督への任命も称号支出もないことを断言する。失敗時はここで止まる。
3. 比較用の支払い総督と通常枠を各1回公式任命する。両者を未配置のまま保ち、GameCoreで取得証跡と使用済み数の増加2個を読む。
4. **未配置時の診断記録を保存した直後**に両方のPlayer証跡が正確に1であることを断言する。未配置の通常枠で読めなければ、ここで失敗する。称号の使用済み数やUI側だけの値から成功にしない。
5. 未配置のまま保存・読込し、証跡、任命状態、会計が一致することを確認する。
6. 配置する都市とターンをGameCoreに記録して完了を待ち、人間の首都へ公式配置する。配置直後と4ターン後は未定着で都市証跡がなく、5ターン後に本体が定着し、配置先の都市証跡だけが1になることを断言する。各時点で21AIの任命・支出も再検査する。
7. 定着後に保存・読込し、本体の配置、定着時間、活動不能期間、Player/City証跡、追加支出の総数が一致することを確認する。

通常枠の任命直後に証跡がなく、発効時点の根拠が必要なら、別の観測シナリオを実行する。このシナリオも最初のAI手番の条件は同じである。任命直後、配置直後、定着後の値を記録し、最後に**元の未配置時の記録**に証跡がないことを失敗として残す。元の値を後の値に置き換えない。

主診断の未配置証跡判定で失敗した場合、後の発効時点は「未観測」と記録する。観測シナリオでは、配置直後だけで証跡が現れれば `SLOT_RECEIPT_AFTER_ASSIGNMENT`、定着後で初めて現れれば `SLOT_RECEIPT_AFTER_ESTABLISHMENT`、定着後もなければ `SLOT_RECEIPT_STILL_MISSING` を失敗理由に付ける。元の証跡がなくても後の定着確認を通した場合、それを主診断の合格には扱わない。

`Lua.log`には次の接頭辞で観測値を残す。元のPlayer/City証跡をLuaから書き込む処理はない。保存する診断記録には別の接頭辞を使う。

| 接頭辞 | 残す事実 |
|---|---|
| `JAC_NATIVE_SLOTS_AI` | 21AIそれぞれの獲得数、使用済み数、枠・支払い総督の任命有無、枠の忠誠圧力 |
| `JAC_NATIVE_SLOTS_OBSERVE` | GameCoreのPlayer証跡、比較用証跡、会計、実ターンと本体総督の配置・定着・活動不能状態 |
| `JAC_NATIVE_SLOTS_CITY` | 所有者・都市IDとGameCoreの都市証跡 |
| `JAC_NATIVE_SLOTS_LOYALTY` | 公式UIと同じAPIで読んだ、配置先都市の忠誠内訳。表示する量からAIの選択理由は断定しない |
| `JAC_NATIVE_SLOTS_FAIL` | 不合格条件。後から発効する証跡を任命直後の証跡に読み替えない |

## UIとGameCoreの保存境界の修正

UIから診断記録を `Game:SetProperty` で保存しようとしていたが、実機のUIにはこの保存用APIがない。UIは総督の状態だけを数値・文字列・真偽値の平らなパラメータで `EXECUTE_SCRIPT` に渡す。Gameplay側は操作を受けてから実際のPlayer/City証跡と称号数を独立して読み、`JAC_SLOTS_PROBE_` の診断記録だけを保存する。配置する都市とターンもGameplay側で記録する。本体の証跡には書き込まない。

各診断記録と配置の記録を送った後に、両シナリオは保存完了を待つ。未配置時の記録は一度だけ作り、配置後の証跡が現れても書き換えない。再読込時は元の記録と新しいUI観測を比較し、再読込の値を元の記録に上書きしない。

専用のRust検査11件とケース一覧の検査2件が成功した。Lua 5.1の模擬環境では、UIで `Game:SetProperty` を呼ぶと失敗する。同期操作を待ち行列に入れ、処理前には診断記録がなく、処理後にはGameplayが読み取ったPlayer/City証跡があることを確認した。両シナリオの `--check` は主44手順・発効観測33手順で成功し、埋め込みLuaの構文も検査した。実機はこの修正でまだ動かしていない。

統合時には配置時計を記録するGameplay側の処理から、UI専用の総督getterも除いた。ここで保存する都市IDとターンは配置要求の目印であり、任命や定着の証拠ではない。UIが記録の完了後に任命・中和状態と配置資格を再確認して、公式配置を要求する。Lua検査ではGameplayの総督getterを取り除いても目印を保存でき、配置前に目印がなければUIが要求を拒否することを確認した。本体のPlayer/City証跡は独立読取のままである。
