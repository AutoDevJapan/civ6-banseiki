# 誓約66件の強い効果を有限手番で測る

Rust生成器は[誓約カタログ](data/sengoku-oaths.json)の22家×3件を、能力診断1本と個別シナリオ66本にする。**能力診断と織田「天下布武」の実機測定を行ったが、全66件・軍事生産速度の数量受け入れは未合格である。** 検査専用の100%補正を切り替えて実測差を物差しにする。物差しを実機で確認できない場合は、最後の数量受入を不合格にする。生成器・形式・Luaの検査成功は、この数量受入の代わりにならない。

生成先は `tools/civ6-autotest/scenarios/oath-effects/`。[一覧](data/oath-effect-scenarios.json)には全66件の誓約、文明、期待する割合、対象と非対象の建造、各シナリオの手番数を記録する。

## 選択と分離

既存の15km日本地図の準備を再利用し、22家・56都市を実所有者つきで確認する。対象家を人間枠に置き、他の21家を残す。全都市で66件の旗が0であることを確認してから、台帳の黄金期だけを検査用に用意する。誓約は本物の選択画面から選び、3候補が対象家のものか、表示文言が正しいか、選択がゲームプレイ側へ保存されたかを検査する。自然な改元が起きたことの証明にはしない。

対象家の全所有都市と他家の全所有都市で、選択前・選択後・診断用の解除後・再適用後を測る。都市ID・所有者・都市中心の区画を照合し、選んだ誓約以外の65件が0であることも各観測時に検査する。対象外の産出、他家の都市、解除と再適用の実数が変われば失敗する。基準が0の産出、住宅で成長が完全に止まる都市だけでは効果を証明できない。

成長を含む誓約では、旗が更新されても成長値が以前のまま返ることがある。成長の数値APIは公式UI側で使い、ゲーム側では呼ばない（実機33でゲーム側の `GetOverallGrowthModifier` が使えないことを確認した）。選択・解除・再適用の各測定では、先にゲーム側で全56都市の所有者・区画・旗・6産出を記録し、画面側で手番と同じ値を照合する。その後、公式CitySupportと同じく産出を読んでから成長を読み、全所有都市のその他の成長補正が直前の標本から変わるまで待つ。変化や一致を確認できなければ60秒で失敗する。更新待ちは値の正しさを認めるものではなく、5%などの割合、解除時の基準への復元、再適用時の一致は従来の厳密な比較で判定する。この修正版の実機測定は未実施である。実機26の切替直後の値だけで、成長補正が安定した後にも残ると断定しない。

診断中の旗の切替や、手番をまたぐときの台帳の一時変更は、本物の選択とは別の証拠として記録する。最後に選択した誓約と全56都市の旗を戻す。

## 公式UIで使われる数値API

根拠はインストール済みの公式資料 `C:/Program Files (x86)/Steam/steamapps/common/Sid Meier's Civilization VI/`。以下の行番号は、このPCの資料を調べた時点のもの。

| 観測 | APIと公式の使用箇所 | 数量受入の条件 |
|---|---|---|
| 生産・金・科学・文化・信仰・食料 | `city:GetYield`。`Base/Assets/UI/CitySupport.lua:316–332` | 同じ都市と同じ種類の100%補正による実測差を要求割合で割り戻して比較する。切替・復元・他家の不変・十分な精度が欠ければ不合格 |
| 成長の割合と総倍率 | `GetOtherGrowthModifier`、`GetFoodSurplus`、`GetLoyaltyGrowthModifier`、`GetOverallGrowthModifier`、`GetHousingGrowthModifier`、`GetHappinessGrowthModifier`。同ファイル486・490・557・570–574、DLC/Expansion2/UI/Replacements/CityPanelOverview_Expansion1.lua:45 | その他の成長補正が要求割合だけ増え、住宅を含む公式UIの式と総倍率の差分が一致すること |
| 軍事・水軍の生産 | `GetCurrentProductionTypeHash`、`GetUnitProgress`、`GetUnitCost`。同ファイル233–257 | 旧66件の `GetYield` 除算は実機12・13で数量契約が成立せず不合格。独立した軍事校正は実進捗差だけで判定し、結果を66件の合格へ転用しない |
| 防壁3種類の生産 | `GetBuildingProgress`、`GetBuildingCost`。同ファイル206–215 | 古代・中世・ルネサンス防壁を個別に指定し、軍事・水軍と同じ実進捗の条件で比較する |

成長の総倍率は住宅や幸福度の影響を受ける。一律に要求割合を100で割った差とはしない。公式 `Base/Assets/UI/Panels/CityPanelOverview.lua:670–672` の式に従い、非占領・食料余剰が正・忠誠度倍率が1の都市で、次の差分を確認する。

`住宅倍率 × {max(1 + 幸福度補正/100 + その他の補正 + 要求割合/100, 0) − max(1 + 幸福度補正/100 + その他の補正, 0)}`

占領・食料不足・忠誠度低下で式の適用条件を満たさない都市は、観測値と理由を記録する。少なくとも1都市で実際に総倍率が増えることを要求する。

産出は、他の加算割合があると「解除時の実効値×要求割合/100」で期待差を求められない。検査専用のPoCは自動で効果を適用せず、公式のPlayer:AttachModifierByIDを検査手順から呼び、所有都市の専用旗を操作する。6産出に各6の検査入力を加え、誓約と同じMODIFIER_PLAYER_CITIES_ADJUST_CITY_YIELD_MODIFIERのAmount=100をオン・オフして実測差を得る。この差に要求割合/100を掛けた量と誓約による実測差を照合し、隣の1%を区別できない誤差幅では数量未確認にする。生産速度を測る前に生産以外の検査入力を消し、最後に生産入力と100%補正も消す。自然な経済や年齢判定の証明には含めない。公式の取付例はDLC/BlackDeathScenario/Scripts/BlackDeathScenario.lua:1204、同じ定量型の資料はBase/Assets/Gameplay/Data/Modifiers.xmlと戦国の誓約SQL。生産キューも、解除時の比率が1でなければ既存補正の計算順を公式Luaだけでは確定できない。その場合、実進捗の増加・復元を観測しても、要求割合の数量確認には数えない。整数の残り手番、SQLのAmount、旗の値だけで数量合格にしない。

## 生産を測る手番

必要な前提技術・社会制度は、読み込まれた建造定義のものだけを用意する。全技術の解禁によるユニットの陳腐化や、防壁を建てられなくなる条件を避ける。下位防壁の用意は公式Tunerの `CreateIncompleteBuilding(..., 100)` を使う（`Base/Assets/UI/Tuner/TunerCityPanel.lua:103`）。自然な技術進行や下位防壁の建設の証明にはしない。

生産は公式の `CityManager.RequestOperation(...BUILD...)` で先頭の項目を置き換える（`Base/Assets/UI/Panels/ProductionPanel.lua:291–370, 2885–2898`）。実所有都市から、公式の開始判定が通り、3手番を測る余裕と都市生産量5以上がある都市を選ぶ。

解除・適用・解除の各1手番を、公式Shift+Enterと同じ `UI.RequestAction(ACTION_ENDTURN, { REASON = "UserForced" })` で進める（`Base/Assets/UI/ActionPanel.lua:1099`）。AIへ操作を渡さず、要求は各観測につき1回だけ。次の人間手番がちょうど1手番後であることを待ち、実数の進捗を測る。途中の完成、項目や費用の変更、手番の飛び、復元失敗は不合格になる。測定前に同じキューで非計測の1手番を置き、その進捗から連続した3手番を測る。生産入力4096を固定し、精度確認用の1%補正と入力1・2は測定中すべて0にする。各手番の前後にゲームプレイ側の全所有都市の生産量と手番を記録し、画面側の選択都市・所有者・区画・手番と照合する。両側の生産量も併記し、手番内に変化するか両側で一致しない場合は数量未確認にする。百分の一という精度を仮定せず、実進捗の差から共通の刻みの上限を求める。固定オフセットは差で除き、二進浮動小数の微小誤差を精度と誤認しない。刻みが大きい・観測不足の場合は数量未確認とする。丸めを含む割合の誤差幅が0.5パーセントポイント未満にならなければ、隣の整数割合と区別できないため数量確認をfalseにする。実機の進捗丸め幅は初回診断と実測で確認する。

軍事の非対象には労働者、水軍の非対象には陸上の槍兵、防壁の非対象には同じ建物系のモニュメントを実際に生産する。同時に都市生産量が増える誓約でも、非対象の進捗をその都市生産量で割った比率が増えないことを要求する。通常進行は産出・成長のみで0手番、軍事・水軍で8手番、防壁で16手番。何百手番も進める処理はない。

### 自然な改元での誓約の失効

`generate-oath-expiry-probes` は、上の保存試験が成功した実機資料だけを入力にする（資料の確認は保存試験と同じ処理を共有する）。読込後のCoreの記録を長さと型付きの鍵で解釈し、保存時の絶対ターン・開始ターン・台帳の元号・旧履歴を取り出す。次の改元の期日は、SSOTの改元表から `Eras_XP1` の長さ×速度の倍率（最低2手番）と日付順で独立に計算し、ゲーム内でも製品の `JAC_Sengoku_Ages.lua` と同じ式で計算して一致を要求する。保存された `ledger.nextDue` は数量試験の人工的な開始（元号1・黄金のみ）の前の値のことがあるため使わない。

生成するシナリオは、元の `enable_mods`、記録された保存名の `exact_name` 読込、保存前後と同じCoreの照合、期日の照合の後、既存の `fast_forward`（`test_mode`）で期日の1手番前まで進める。飛ばすのはエンジンの手番だけで、台帳・年代・元号・誓約・旗・履歴・イベントは書き換えない。実際に飛ばした手番数は実行器の `test_mode.skipped_turns` に記録され、`continuous_performance_valid` は false のまま。期日へは画面側とCoreの準備完了を待ってから公式の終了要求1回だけで進め、ちょうど1手番後を待つ。期日では、製品の `OnGameTurnStarted` による判定が1回だけ行われ（新しい履歴1件、旧履歴は不変、全22家の結果）、人間の選択が空・期限が翌手番・全都市の旧誓約の旗が0であることを確認する。AIはこの改元で既定の選択を受けるので、人間の条件はAIに当てはめない（英雄の年代は3つすべて、選択肢が無い家は選択なし）。翌手番は補助の確認で、人間に既定の選択が合法に入ること（同じ誓約が再び選ばれてもよい）と、判定の記録が変わらないことを確かめる。
