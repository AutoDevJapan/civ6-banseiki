### Artifact個別MP MOVE：UI制約と現本体の直接移動を分離

この節の「新規5件」「関連10件」「計11件」は、独立した初期候補の限定検査である。このブランチの差分には、中止後の再準備、保持中の重複観測、別ターンの合法な作品移動、キューでの占有交換を追加した。これらは実機や実LANでの成功を示さない。

このブランチのRust結合検査 `carrier_sync` は、配布Gameplay LuaをLua 5.1で読む71件が成功し、省略は0件だった。中止後に古い作品一覧で次の準備が止まる問題と、保全中の同一観測を繰り返し保存する問題は、修正前の失敗と修正後の成功をそれぞれ確認した。全workspace・本体実機・実LANの結果とは分ける。

今回の接続は、借用可能な元都市と受取先都市を一時的に同じ適法人間Actorの所有へそろえ、元indexを空の適合枠へMOVE一回で移し、都市を返還する経路である。原本生成・Core Enact・占有枠とのswapは使わない。既存Artifact CITY継承の模擬検査や旧SP成功記録を新MP実通信成功とは扱わず、実機・実LAN0回を維持する。

一次根拠は公式GreatWorksOverview.luaの七つのPlayerOperation引数と、[本体操作の作者解析](https://cru121.github.io/civ6-gamecore-reference/operations/player-operation/MOVE_GREAT_WORK.html)。現FinalRelease DLLのPlayer::Operations::Manager::Processも読み取り専用で照合した。MOVE hash `0x291d387e` のcaseはRVA `0x30e6ed`〜`0x30eade`。PARAM_PLAYER_ONEから得た同一Playerの都市集合で元と先のIDを検索し、先の指定建物・枠のindexを読んでから元indexをRemoveGreatWorkする (`0x30e8a0`〜`0x30e920`)。先が空なら `0x30e926` からswapを飛ばし、`0x30ea72` のAddGreatWorkToSlotで元indexを指定枠へ置く。このcaseには作品種別・museum満枠数・作成者履歴の条件は現れない。よって公式UIの「満枠Artifact博物館同士」の交換制約をCoreの直接MOVE禁止には読み替えない。

先が占有されている場合は本体に交換分岐が存在するため、その分岐は製品で利用しない。Gameplayは共有観測の元枠・先空枠・枠適合を照合し、Actor UIは自身からMOVE要求を出す直前に先枠の空きを再読取する。このUI読取と本体キューの実行を原子的につなぐ公開APIは確認していない。読取後に別の操作で先枠が埋まり、本体が交換した場合は、模擬検査では両作品を一件ずつ保持して都市を返さず、成功扱いを拒否した。実LANでの配送順序と交換後の復旧は未確認である。

UIが先枠の占有または読取失敗を検出したときはMOVEを送らず、そのセッション内に`NOT_SENT`を保持する。後続の観測が届き、元作品が元枠に一件残り、先枠が空いた後の都市・作品を照合できた場合だけ、借りた都市を返す。先枠に別作品がある間は、その作品を返還先へ移してしまうおそれがあるため都市を保持する。同じ候補の一時的な占有が解ける機会を残すが、中止が初回を含め3回に達したら止める（再試行は最大2回）。送信後の結果が不明な場合は`UNKNOWN`としてMOVEを再発行せず、原枠の観測だけでキューが空になったとも推測しない。保持中の同一観測は再検査しても同じ内容を繰り返し保存しない。

借用中に操作担当が無関係な作品を動かした場合も保全状態に留まり、自動復旧しない。先枠で交換が起きた場合と併せ、ゲーム内の実所在を調べて人が復旧する経路は未実証である。別ターンのRECHECKは世界一件性と来歴を照合するが、他作品の所有者変更の合法性までは判定しない。

公開CanStartOperationにつながる本体CanStartは、request組立てとhandler検索の後、旧来のMOVE caseでは共通判定へ進む (`0x30c2a0`〜`0x30c369`)。共通判定 (`0x30c100`〜`0x30c293`) はActorの存在、活動状態、戦略操作が許されるphaseを扱い、手番外のMOVE hashを拒否する分岐がある。また人間とGame状態の条件を検査する分岐もあるが、単一フィールドの意味を推測して「MPでは無条件に許可」とは説明しない。Artifact満枠・先空枠条件はこの共通判定にはない。操作送信のエンジン側Actor認証・実配送同期範囲は実LANで未確認として残す。MOD側は保存された唯一の人間Actorの活動手番だけで送信し、Gameplay同期callbackがエンジンから受けたactor、phase、nonce、token、保存intentを検査する。PARAM_PLAYER_ONEも同じActorとし、AI本人への偽装はしない。

実装はArtifactの一律拒否を、借用・枠・来歴・唯一性の検査に置き換えた。PREPAREで両都市の他の原作品のindex・元枠・来歴・効果と世界一件性を同期観測として保存する。借用中と返還中は、原作品の欠落・重複・枠替え・来歴差替えを拒否する。中止して都市を返した後は前回の作品一覧を消し、次の候補を新しい一覧で準備する。完了後の別ターンの再確認では、他の作品の合法な配置替えを許す一方、来歴と世界一件性を保つ。読めるCore slot getterは優先して照合する。UIのみの値は保存されたActorの同期観測として扱い、独立したCore証拠とは表記しない。Artifactの借用途中記録に作品一覧がない場合は推測して補完せず停止する。

### 初期一覧と通常CITY継承の共有観測

初期作品一覧とキャリアの関連検査は75件すべて成功し、省略は0件だった。作品一覧16件とキャリア59件に、独立したLua 5.1環境、保存状態の再構成と再参加、部分送信、重複要求、無資格の実行者、都市継承後と翌ターンの照合を含む。配布LuaとRust生成源の一致も確認した。この結果は実LANの成功を意味せず、最終レビュー・全workspace・CIとマージは別に確認する。

旧候補3847d926は9件成功・2件失敗だった。都市情報の複製にエラー文が余分な引数として渡る本体の不具合と、検査の保存再構成で生成済みユニットが失われる不備を修正した。さらに作品の借用・移動・返還後、正式吸収で元都市の所有者とIDが変わる結合不具合を失敗検査で再現して修正した。都市移管後のCore IDを保存し、最新の共有観測から作品の唯一性、指定枠、元枠の空きを照合する。旧失敗のログは保全し、最新の成功へ読み替えない。
初期NativeWorks一覧、Flowの再照合、取引の準備、CITY継承後の照合は、MPでは同じ保存snapshotを読む。Gameplayが都市の所有者・ID・座標・建物・名前・人口・登録済みプロパティを直接採取する。作品枠、忠誠、宗教、区域や来歴に直接getterが存在する場合も、そのCore値を優先・照合する。全項目をCoreだけで読める場合はUI要求を必要としない。

観測の復号は通信量1MiB、深さ24、各表4096項目の範囲に制限し、節点数は入力のバイト数に応じて数える。80都市相当の観測を往復する検査を通した。処理済み要求は同じターンの重複照合に必要な各片の長さと二つの検査値だけを残し、都市一覧・観測・実行計画は消去する。次ターンには処理済み記録も整理し、終了・取消し済みの取引に属する未使用要求も消去する。未完了の要求と部分受信は保持する。旧保存の受信本文からも検査値を復元し、再送で都市移管を繰り返さない。都市情報が同じターンで変わった場合は古い要求を受け付けず、番号を更新して新しい観測を待つ。

直接読めない項目は、Gameplayが生存人間の最小IDを提供者に固定し、その本人の手番でUIから観測し、公式EXECUTE_SCRIPTで同期する。エンジンが渡す実行者、保存意図、phase・nonce・手番とCore都市情報を検査して保存する。提供者は最終受取人とは別で、AIの受取先でも提供者は適法な人間である。UI由来の位置・来歴をCoreの独立証拠と呼ばず、証拠種別を保存する。UI公開は切り離した未処理要求の読取だけで、要求作成と再開・提供者更新はGameplayが担当する。

通常CITY継承は既存Core都市移管を各都市一回だけ実行し、個別MOVEを要求しない。移管後の所有者をCoreで確認し、共有観測で原index・建物・枠・来歴・効果と世界一件性を再照合してから完了する。各端末のUIキャッシュが異なる、欠ける、公開が遅れる場合も、その値をGameplayの分岐・保存へ読み戻さない。欠測は同期観測待ち、日本語の文字境界を保持した分割受信は全片がそろうまで未確定のまま保存する。重複RPCは保存receiptで処理し、送信結果不明でも都市移管は再発行しない。

### 回収前の所在変更と人間所有の宮殿

作品の枠種別は回収対象の原本について照合する。そのgetterだけがGameplayにない場合は回収の共通UI観測を待ち、通常のCITY継承等の直接読取は維持する。旧保存で原本の来歴が欠けている場合は、欠けた項目を診断して原本と意図を保留する。現在の観測値だけで過去の来歴を作り足したり、原本を再生成したりしない。

回収を始める前に、原本の現在の所在を共通の作品一覧で確認する。保存した保管都市が征服された場合や本体の適法な配置替えがあった場合も、世界に一件の同じindex、種類、創作者、作成ターン、作成者と効果が一致したときだけ、未借用の回収元を現在の枠へ更新する。保存時の保管人から別の第三者へ所有者が変わっていた場合は、その都市を新たに借りずに待つ。受取人の既保有と人間所有の宮殿から本人が移す経路だけを例外にする。借用を始めた後は元の意図を更新しない。原本がすでに受取人の枠にある場合は、共通観測に基づいて回収を確定し、作品に適合する現在の枠種別も共通観測で照合し、追加MOVEや都市借用を行わない。保存時の物理所有者も同じなら、所有者変更の記録数は増やさない。提供者の認可・保存再構成・再参加・古い要求の拒否は初期一覧と同じ境界を使う。観測待ちは世界報酬の待機状態を保ち、公開された後は保存した受取人の報酬だけを再開する。

現在の原本が人間の宮殿にある場合は、その所有者本人を操作担当に固定する。首都は本人の領土に保持し、受取側の適格な非首都都市だけを借り、同一所有者内の公式MOVEを一度発行して返す。元の宮殿の別作品も観測対象に含める。借りない本人の都市では駐屯部隊を移さず、現在のCore一覧と照合して保つ。本人の手番待ち、受取人による無資格送信、保存後の再構成と重複処理を検査する。公開された回収入口からこの経路を扱えるが、吸収元を人間に変更するものではない。AI所有の宮殿作品と考古遺物の交換は未対応であり、この条件付き経路を全体の完了に数えない。本体の完全な所有履歴は証明できておらず、新規の危険なCore再取引は解禁しない。

MPでは人間の操作担当を保存し、必要な二都市をその人へそろえて公式MOVEを要求する。人間の取込先は本人、AIの取込先は生存する人間の最小IDを操作担当とし、その人の手番を待つ。散逸先と回収先は操作担当とは別に保存する。配布するGameplay・UIのLuaはRustのキャリア生成器から作る。以下は独立Lua51 VMの自動検査で確認したコード経路であり、実LANの成功を意味しない。実通信の確認は後日の友人とのプレイで行う。

書き戻す都市プロパティは、Gameplay内の登録済み都市プロパティ一覧と統治キーだけを対象に、Coreの各都市から直接採取して保存する。UIが送るキー一覧・値はCoreの実測と厳密に照合し、UIの値を復元用の原本として採用しない。任意キーの注入、登録値の変更や省略は借用前に拒否する。Core用accessorはUIへ公開しない。Coreは都市の所有者・ID・座標、名前・人口、建物の存在、中心部隊と登録済みプロパティを自分のgetterから照合する。作品枠・忠誠・宗教にも直接のGameplay getterがある場合は、UIを経由せず現在のCore値と照合する。Getterがない値、全世界の作品位置、購入区画などは、選ばれた実行者の同期観測であり、Gameplayによる独立した実体証明と表現しない。

AI所有の宮殿、占有枠との交換、借用できない首都・最後の都市からの個別移動は、全作品を事前に検査して最初の都市借用より前に拒否する。通常の都市継承は個別MOVEの制約と分ける。移動先候補はUIから一覧を送り、Coreが適法な候補を選ぶ。首都・最後の都市・占有中心などの不適格な先頭候補を繰り返し選ばない。

二都市の借用前には全都市を検査し、各移管の直前にも照合する。途中失敗では発行済み意図・座標・現在のCore所有者とIDから、実際に借用した都市だけを返還する。返還途中の失敗も保存し、残りの返還とCore由来プロパティの復元を再開する。MOVEは準備、送信権の確保、要求送信を分け、送信権を確保する前のセッション再作成は原枠の同期観測を経て取り消せる。古い送信権確保の要求はphase・nonceで拒否する。明示的なネイティブ要求拒否は、原枠を再観測してから返還する。

送信権を確保した後の切断や返り値不明では、原枠にまだ作品があるという観測だけでキューの終了を仮定しない。MOVEを再発行せず、都市と意図を保持する。遅延していた原本の移動を同期観測した場合は返還へ進める。キューの未実行・終了を確認できない状態に時間切れだけの返還は設けない。旧Version 1のUI由来復元記録も、Coreの元値を裏付けられないまま復元へ流用しない。

借用中の名前・既存の建物や区域・他の作品・中心部隊・既存の購入区画の保持条件と、人口・忠誠・信徒・登録済み値の自然な変動を分ける。変動する値をPREPARE時の全状態へ固定しない。返還直前には現在の登録済み値をCoreから保存し、所有者移管でプロパティが消えた場合もその値を戻す。返還の意図と原本は移管前に保存するため、途中失敗で消えた値を後から空の観測で置き換えない。返還済みの都市は所有者とIDを再確認し、古いプロパティの再復元を省く。まだ復元記録がない場合も、現在のCore値がある項目は保持して欠落分だけ補充する。例外を都市ごとに記録し、1都市の失敗が他の返還を止めないようにする。返還完了後の合法な更新も古い保存値との不一致だけで拒否しない。CLAIM前の型・形・未登録キーなどが不正な観測は取り消す。転送直後の古いUI値で出うる不一致は同じnonceで3回まで待ち、正しい観測で待機回数を消す。3回続く場合は都市を返し、phaseとnonceを進めて古いCLAIMを遮断する。借用・返還の取り消しは1キャリアにつき3回で止め、返還済みの状態を保持する。CLAIM後に送信有無が不明なMOVEを取り消す条件は緩めない。

人間の手番待ちはWAITING_UIにする。手動の非Flow取引で手番をまたいだ場合、保存されたMPキャリアの継続と返還だけを許可し、古い部隊・都市・追加アダプターの契約は再実行しない。その後の吸収処理には正規Flow契約の再検証が必要であり、手動取引全般の同一手番制約は維持する。FlowPolicy付きの正式取引は既存の継続契約に従う。元ToDo996の宮殿・考古遺物・散逸・回収と実通信の未達条件は保持する。

## 保存単位と失敗時の扱い

画面側の英雄管理表はゲーム処理中の変更が即時には見えない。生成した候補のIDを保存し、画面側がゲーム処理の更新を受け取って照会結果を公開するまで `WAITING_UI` として返す。これは成功でも自害でもない。呼出側は次の処理段階で同じIDを `A.Resume` し、候補を増やさず照合する。更新後にも管理表が一致しない英雄だけを自害として確定する。保存用の表に候補IDと待機状態を残す。Luaスクリプトの再初期化は検査済みだが、待機中の実際のゲーム保存・読み込みと再開は未検証。シナリオは一度のLua処理を終えてから待機・再開し、実ターンを大量に進めない。

人物・所持品・宗教・知識は各 Player の `JAC_ABSORPTION_ASSETS_V1` に、固有 ID をキーにした表で保存する。最低限の形式は `{ID, Kind, Owner, ...}`。`Kind` は `PERSON` / `HERO` / `GREAT_PERSON` / `ITEM` / `UNLOCK` / `RELIGION`。人物の `Unit={Owner,ID}` と都市所蔵の `City={Owner,X,Y}` は移管先へ付け替える。`Anchor={Kind,ID}` の固有 ID、宗教の Founder、その他の歴史上の ID は変更しない。

Game の `JAC_ABSORPTION_STATE_V1` に入力、元データ、置換 Unit の対応表、都市・領土、処理状況、移管されない資産を保存する。Unit の `JAC_ABSORPTION_UNIT_TOKEN_V1` は「処理 ID＋旧 Unit ID」の永久の識別子。Unit ID が変わっても追跡できる。既存の成長 PoC の `JAC_POC_GROWTHUI_WARLORD` も複写する。空文字列は保存しない。nil で削除する。

一般 Unit の順序は、入力検査 → 保存 → 全 Unit の生成・復元・照合 → 旧 Unit の除去 → 都市と領土 → 人物・所持品・宗教・知識 → 統合口 → 最終照合。最後の都市を移した際に旧文明の Unit が消える場合にも、一般 Unit は先に生成されている。

公式英雄は召喚元の都市が必要なので、この順序に例外がある。一般 Unit を先に復元・検査し、英雄の本体・人物・管理表の状態を保存してから旧英雄を除去する。都市を移した後に同じクラスを生成し、保存した ID 集合、クラス、管理表、召喚元を照合する。英雄専用の失敗なら候補が自分の処理で新しく発行されたことを確かめて除去し、人物を自害の履歴へ移す。都市・一般 Unit・資産・統合口の失敗は従来どおり `BLOCKED` とする。権利を継承できない休眠中の英雄も、吸収全体は止めずに自害の履歴へ移す。

英雄には生成前の Unit ID 集合と候補 ID を保存する。生成 API が例外を投げても、正しい所有者・クラス・召喚元を持つ候補が1体できていれば採用する。確認できない候補や別の取引のトークンは削除しない。第三勢力の Unit は削除しない。候補が複数あるなど帰属を決められない場合は `BLOCKED` とし、成功や自害の確定を装わない。元の入力は `Request` に保存し、実際に自害へ変わっても同じ入力の再実行だけを受け付ける。

実際の再召喚は、ゲーム側で `A.BeginHeroRecall(recallID, transactionID, recordID)` を呼び、UI 側で公式画面と同じ `CityManager.RequestCommand(..., PURCHASE, ...)` を発行した後、ゲーム側で `A.CompleteHeroRecall(recallID)` を呼ぶ。開始時に既存 Unit ID と人物記録を保存し、完了時に新しい1体だけへ専用トークンを付ける。人物レコードと Unit の人物プロパティの双方を新 ID へ更新し、契約・忠誠・関係値を保つ。候補がない、複数いる、別のトークンを持つ場合は記録を書き換えずに停止する。現 PoC に一般プレイヤー向けの購入 UI フックはなく、2本目の実機シナリオがこの順序を実行する。

英雄以外の失敗と、候補の帰属が判断できない場合は `BLOCKED` と理由を保存し、成功と報告しない。失敗前の都市・Unit・プロパティのスナップショットは残る。ただしエンジン変更全体のロールバックではなく、途中の置換 Unit が存在し得る。同じターンの `A.Resume(id)` は保存した Unit トークンを発見して重複生成を防ぐ。参照の期待値を計算し始める前に対応表全体を固定する。期待値が一部だけ完成した段階でも、参照先の Unit を別 ID へ生成し直さない。受入側の資産は現在の一覧へ移管分だけを加え、処理の途中で追加・更新された別資産を上書きしない。移管元の一覧が途中で変わった場合も、新しい資産を黙って消さず処理を止める。次のターンへ進んだ後の失敗復旧は自動で行わず、判断が必要として拒否する。完了した同じ入力の再実行は処理を繰り返さない。同じ ID に別の入力を渡すことも拒否する。

本体 Unit の傷、残り移動、経験値、昇進、編制、名前、偉人個体と能力の残り回数、宗教、建造・布教回数を対象にする。移管するネイティブ偉人の能力回数を取得できなければ、エンジンを変更する前に拒否する。消費済みの建造・布教・偉人の能力回数を新 Unit で再現できないときは、旧 Unit を消す前に止める。護衛リンク、交易路、進行中の作業・任務、Unit が持ち歩く未設置 Great Work、未登録の他 MOD のプロパティはこの方法だけでは移管できない。利用する機能がある場合は先に統合口で加入可否を検査する。これらを保存済みと主張しない。

`A.Verify(id, true)` は同じターンの完全な照合用。後のターンには通常の行動で傷・移動・経験値・信徒数が変わるので、実機シナリオは進行後の現在値を新たに保存し、その保存前後の同一性を比較する。

## 公式英雄の未解決点と実機確認

- **名声**：導入済み DLL と実行ファイルに `GetRenown` / `SetRenown` の Lua 登録が見当たらず、`UnitPropertyKeys` に対応する公開名も見当たらない。人物記録の `Renown` はそのまま移す。実行時に旧例の Getter と Setter が存在する場合だけ本体の値も復元する。存在しない場合は `NativeHero.RenownUnavailable=true` として保存し、本体の名声を保存できたとは主張しない。
- **召喚履歴**：公開されている変更口は新規生成の `CreateHero` であり、権利だけを移す Setter は見つからない。この呼出しは受入側に新しい召喚履歴を作る。旧所有者の内部の召喚時代・召喚ターン・再召喚履歴を読み出し、同一の値で受入側に移す API は確認できない。元の英雄が以前の時代から存続する場合や既に再召喚された場合について、以前と同じ再召喚制限・費用になることは保証しない。実機シナリオの2体は同じ時代に初召喚した例である。
- **死亡済みの英雄**：移管元だけが権利を持ち本体 Unit がない場合、公開 API で権利を移せない。取得できるクラス・旧所有者・召喚元・既存の人物記録を自害の履歴へ保存する。受入先に召喚権ができたとは報告しない。
- **生成失敗後の管理表**：`CreateHero` は本体を作れなくても権利の所有者を変更し得る。自害の記録には失敗後に読み取れた `NativeClaimAfter` を残す。管理表の権利を取り消す公開 API は未確認であり、自害の記録だけで本体の再召喚を禁止できたとは主張しない。
- **本体の副作用**：残り寿命の書戻しと再生成が本体の作品・信仰費用・召喚制限へ及ぼす影響は未確認。実機シナリオは Great Work の数と費用の実際の変化を残す。元からある作品の消失は照合で検出する。内部召喚履歴の保存を推測しない。
- **実際の再召喚**：2本目のシナリオが人間の織田家で購入命令まで実行する。購入 UI と人物記録の結合は PoC の2つの API を順に呼ぶ方式であり、通常のゲーム画面からの再召喚すべてに自動で適用される機能はまだない。購入が拒否されたり候補が紛らわしかったりすれば検証は失敗する。

## 残る実機確認

宣教師の比較対象は同じ所有者・宗教・布教回数と移動力で生成し、両部隊の開始座標と移動力を記録する。生成可能な隣接位置は元の位置と異なり、部隊一覧への追加がAIの選択へ影響する可能性もある。比較結果は診断の手掛かりとし、それだけで通常のAI行動や移管不具合と断定しない。元の移管部隊が消えた場合は引き続き失敗にする。

画面側の値に依存する単独検査は、`RequestVerification(id)`、公開完了の待機、`Verify(id, exact)` の順で実行する。公開した要求は検査時に消費するため、同じ要求を再利用して古い値を正しい状態と報告できない。要求から検査まで資産を書き換えない。内部の照会要求番号は検査のたびに増えるので保存比較からだけ外し、取引・履歴・資産は全件を比較する。部隊がいない勢力の都市情報も、移管前の公開完了を待つ。

一般部隊と偉人は受入側の首都で準備する。海や空の部隊などをその近くに置けなければ、地図上の配置が確認できるまで停止し、元の部隊を消さない。確認した候補を増やさず再利用する。都市と領土を移した後は、保存した元の位置へ移し、移動残量や傷を復元して再検査する。
