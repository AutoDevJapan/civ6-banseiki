# Civ6検証ドライバーのRust移植

PR87の検証ではPythonを新たに実行せず、`tools/civ6-autotest-native/` のRust製モジュールを使う。2026-10-02、オーナーが既存Pythonの例外を認めず、移植後に実機検証を続ける方針を選んだ。

## 対応する検証

対象は日本吸収127手順、英雄再召喚101手順、宣教師診断13手順である。既存JSONのLua命令と検査条件を読み込む。RustからFireTunerの公式接続へ命令を送り、ゲーム内Luaで検査する。Pythonのソースは移植時の参照資料であり、実行・import・機能追加を行わない。

対応する操作は再起動、MOD切替、設定、開始、Lua、待機、保存、メニューへの終了、読込、手番終了、自動進行、待機時間の指定である。未対応のスクリーンショットや性能計測などが指定された場合は、実行前に失敗する。省略して成功とは扱わない。

- 起動はSteamのDX11指定を使い、複数プロセスを拒否する。実行ファイル・PID・生成時刻・対象ウィンドウを照合し、既存と同じウィンドウ宛メッセージでキーを送る。
- MODのGUID・重複・導入、更新時刻、DDSとBLPに含まれるアトラス名を検査する。
- Lua命令の応答が不明な場合は、その命令を再送しない。開始・読込による接続切替では、同じ命令を送り直さず画面遷移を観測する。
- 保存名を実行フォルダごとに分け、既存の保存を上書きしない。保存完了のイベントと非空の実ファイルを照合する。
- 元のLuaの取得値を保存し、読込後の値との完全一致を検査する。
- 検証モードの早送りは時代境界を通常処理し、省略数を記録する。連続性能の測定とは扱わない。
- ログは保存世代・位置・ハッシュで範囲を管理する。必須ログの欠損、空の証拠、JACのエラー・実行時エラー・テクスチャ欠損を合格にしない。

## 標準の実機ツールとの接続

ゲーム資源の保持、待機列、30分の譲渡は引き続き `D:/CC/Tools/civ6-live/live_chain.exe` が担当する。独自の共有ロックや待機処理は作らない。

現在の標準ツールは、検査対象のブランチにある `civ6-autotest-rs` をビルドして呼ぶ。[共有ツールへの接続](../tooling/civ6-live-rust-driver.md) を参照する。以前の吸収検査では、実行元プロセスだけに `CC_LIVE_PYTHON` を設定し、Rust 製の代替実行器に入口の位置引数を渡していた。これは当時の接続方法の記録であり、現在のブランチでは環境変数の設定は不要である。

標準ツールが再起動を加える場合も、元の127・101・13手順を全て照合する。結果は `result.json`、`steps.jsonl`、通信出力、ゲームの3ログへ保存する。結果の保存に失敗した検証を合格にしない。

全シナリオのLua構文をゲーム操作なしで確認する場合は、`cargo +stable run --locked --manifest-path tools/civ6-autotest-native/Cargo.toml --bin scenario-lua-audit -- tools/civ6-autotest/scenarios <期待するJSON件数>` を使う。JSON内の命令・待機条件を再帰的に収集してLua 5.1としてコンパイルする。件数の不一致、命令が一件もない場合、構文エラーは失敗にする。これは構文確認であり、実機でAPIが公開されることや操作が成立することの証拠にはしない。

## 検査と現状

最終候補 `402bb309f05178d85e0e7adc591b33b612002ac1` では、本体52件・英雄観測生成器4件・日本受入生成器5件の61件が成功し、省略0件だった。形式検査、警告0件の静的解析、実機用releaseビルド、元の127・101・13手順の全Lua片の構文検査も成功した。候補のWindows Rust CIとCodeQLも成功した。

同じ候補の日本吸収48は133/133、英雄再召喚49は102/102、宣教師診断50は14/14手順を完了し、各3項目のログ判定も全て成功した。日本の元127手順には準備5手順を加え、3本それぞれに標準ツールが再起動1手順を加えた。元の受入条件・取得値・順序は保持し、画面側の退役記録の読取だけゲーム処理側の同じ値を返す窓口へ接続した。保存5件の実ファイルと保存前後の完全一致を確認した。

日本の追加準備は、退役記録の読取と待機、検査資金の整数部の退避と復元、読込後の同じ取得項目の再登録である。短い観測診断43の19/19手順で、AIが時代待機中に信仰1000を払い対象英雄を作成したことを確認した。通し受入では、生存中と同時代の拒否を資金付きで検査した後、明示的購入の直前まで整数部だけを退避する。実際の端数と待機中の増加分は本体に残し、後で整数部を足す。英雄の削除や代行購入は追加しない。

資金復元の追加検査は、短い精度診断46の7/7手順で観測したgetterの丸めに合わせた。大残高の読み出しは単精度相当と推定され、1,000,007.046875という計算値に対して1,000,007.0625が返った。小残高を計算上の端数へ再設定せず、その実残高を残したまま整数部を戻す。丸めを適用するのはこの追加準備の期待値だけであり、元の実支出・費用・生成・保存の比較には適用しない。読み出しの丸めを、ゲーム内部の残高が完全に同じ精度である証拠とも扱わない。

最後の保存比較では、取得項目を削除せず、読込前と同じ所持品キーを登録し直して完全一致を検査した。実機47の差はこの登録だけであり、48では全取得項目が一致した。証拠は [吸収PoC](absorption.md) と [再開記録](../worklogs/pr87-recovery-20261002.md) にまとめた。

通常691件・旧ドライバー252件・吸収Lua120件は前担当の実測で、今回Rustで同件数を再実行したとは主張しない。短い観測・精度診断も3本の通し成功とは区別する。検証モードは連続性能やマルチプレイの検証には使わない。
