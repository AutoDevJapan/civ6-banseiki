# Civ6の起動停止と復旧

起動待ちのタイムアウトは、ゲームの開始画面が応答しない問題と、共有された表示処理の停止を区別して扱う。Startup.logの最終行が`SetupBinarySerialization()`でも、その処理が原因とは限らない。メニュー到達が成功した実行でも同じ最終行を確認した。

## 2026年10月3日の実測

ゲームの起動と終了は、すべて`D:/CC/Tools/civ6-live/live_chain.exe`の共有ロックを通した。対象はmainの`9872fea`にあるRust実行器。Steam URIからDX11版を新規起動し、他の担当のゲームやジョブは終了しなかった。

| 比較 | 結果 |
| --- | --- |
| 復旧前、オーバーレイ有効 | main-12の起動待ち120秒が失敗。終了要求後もゲームとNVIDIA Overlayが残り、GPU状態の照会も応答しなくなった |
| NVIDIA Appでオーバーレイを無効化 | 設定は反映されたが、既に停止したゲームと表示処理は復旧しなかった |
| 前回と同じWindowsの表示復旧操作 | 03:30:48 JSTに残留プロセスが消え、GPU状態の照会が直ちに戻った |
| 復旧後、オーバーレイ無効 | main-13で新規起動、メニューの可視性、FireTunerのFrontEnd応答が成功 |
| 復旧後、オーバーレイだけ再び有効 | main-14も成功。有効という設定だけで毎回停止するわけではない |
| 最終設定を無効に戻して3回連続起動 | main-15の9手順・5判定が成功。03:36:33–03:38:12 JST。各回のメニュー画像を目視し、FrontEndの照会が3回ともtrueを返した |
| 新しいNVIDIA部品を読み込んで有効のまま3回起動 | main-16の9手順・5判定も成功。稼働中のゲームで録画部品11.0.9.251、描画ドライバー32.0.16.1062、Steam部品10.96.30.42を確認した |

3回の起動完了までの時間は約24.5秒、36.4秒、36.2秒。既存メニューの再利用は数えていない。試験後にゲームを終了し、共有ロックも解放した。

DX11のRenderer.logはRTX 5090を選択していた。AMD内蔵GPUへの誤選択ではなかった。復旧後も分類用コンテナとOllamaのモデルは稼働を保ち、GPU使用メモリは約29GB、空きは約3GBだった。モデルの停止やVRAM設定変更は、この成功の前提にしていない。Steamオーバーレイも変更していない。FiraxisLiveは復旧後の起動でログインと権限取得を完了した。

## 停止中の証拠と留保

03:15:59 JSTに、終了要求前のPID134228からダンプを採取した。Rustで143スレッド、1,008フレームを、時刻・サイズ・CodeViewが一致するPEの復元情報から解析した。主スレッドはSteamのオーバーレイからDXGI、D3D11を経由し、名前なしSemaphoreを2秒待っていた。前回の終了後ダンプと21フレームすべてが一致した。

この実測と表示復旧の結果は、共有された描画処理の異常を支持する。Semaphoreを通知する側や、最初に異常状態を作った部品は特定できていない。ログイン待ちを主原因とする証拠も得られなかった。

停止時に読み込まれたNVIDIAの録画部品は11.0.7.247だった。今回の調査中にディスク上の版は11.0.9.251へ変わっている。Overlay.exeの作成時刻も03:18:03 JSTだった。更新ログには03:17:52 JSTのNVIDIA自己更新タスクと、約03:18:02の新しい録画部品のコピー成功がある。main-16では新しい録画部品の読み込みと3回の成功を確認した。main-13/14が読み込んだ録画部品の版は未確認であるため、オーバーレイの無効化だけで原因を取り除いたとは断定しない。NVIDIAは11.0.9で複数GPU構成の動画再生と統計表示の互換性修正を公表しているが、今回と同じ不具合かは未確認。[NVIDIAのリリース情報](https://www.nvidia.com/en-us/software/nvidia-app/release-highlights/)

最終設定はNVIDIA Appの`Settings > Features > NVIDIA overlay`をOffにした。長時間稼働したオーバーレイのGPU占有と残留を避けるための対策であり、DLLやレジストリを直接編集する手順ではない。

## 復旧時の操作

前回のRust補助プログラムからWindows+Ctrl+Shift+Bを送った。これはMicrosoftが案内する表示ドライバーの復旧操作である。[Microsoftの説明](https://support.microsoft.com/en-us/windows/hardware/display-graphics/troubleshooting-blank-screens-in-windows)

03:30:48 JSTの操作では、自分のlive_chainが持つロックを読み取りハンドルで保護し、GPU Engineの全利用率が3回の標本で1%未満だったことと、Ollamaの処理が待機中だったことを確認した。GPU処理が稼働していた2回の試行は操作を送らなかった。復旧後、Ollamaは同じプロセスから正常応答を続け、分類用コンテナも同じ開始時刻・PIDでhealthyを保った。

PC全体の再起動、GPUデバイスの無効化、Docker/WSL/Steamの再起動は行っていない。

## Rust実行器の自動復旧

新規起動したDX11プロセスが開始画面の待ち時間を使い切り、FrontEndに到達していない場合に、成果物の`startup-recovery-<識別子>/`へ診断を保存する。各試行のログ、ゲームの画像、ミニダンプ、プロセスとメモリの情報、時間を制限したGPU照会を、終了要求より先に採取する。復旧の判断と結果は`recovery.json`に記録する。

プロセスのハンドルと作成時刻、起動要求の時刻、DX11ウィンドウを照合する。FireTunerの設定が無効、ログイン通知などで既にFrontEndに到達、中断、別プロセスの出現、共有ロックの喪失では表示復旧を行わない。

復旧操作は、live_chainが渡す所有者とロックの場所を検証し、読み取りハンドルでロックを保護したまま行う。ゲームの終了要求後も元のプロセスがGPU待機で残っている場合は、終了待ちだけで打ち切らず、安全判定を通過した表示復旧の後に終了を再確認する。

WindowsのカーネルからGPU一覧とエンジン数を取得し、PDHから全エンジンを1秒間隔で3回採取する。NVIDIA・AMD・WSL・CUDAをエンジンの名前で除外しない。カーネルがソフトウェア装置と明示した識別子も保存し、未確認のGPUと区別する。いずれかの処理または合計使用率が1%以上、GPU・エンジンの不足や変更、古い観測、キーの押下中では復旧操作を送らない。NVIDIAの状態照会が停止していても、独立した完全なPDH情報で安全を確認できる場合だけ判断を進める。

安全を確認できなければ、表示復旧を省略した理由を残す。元のゲームが終了していれば、一度だけ新しい待ち時間でSteam経由の起動を試す。元のゲームが残る場合は追加の起動を行わない。2回目も停止した場合は診断を追加し、3回目を起動しない。共有ツールには再試行済みの目印を渡し、外側から同じ試験がさらに繰り返されることを防ぐ。

共有ツールのソースは`D:/CC/Tools/rs/cc-live`にある。[変更差分](civ6-startup-recovery.patch)に、診断プログラムのビルドと出所の検証、所有者の受け渡し、重複する再試行の停止、対応するRustテストを保存した。
