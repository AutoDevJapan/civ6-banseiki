# 実機試験の基盤を確かめる

製品の試験を再試行する前に、基盤だけの保存読込を10回続けて確認する。失敗した試験を次の担当が同じ入力で繰り返しても、合格回数には足さない。

## 最小の試験

`reliability-seed.json` で、決まった乱数と小さな地図を使い、エジプトとシュメールの2文明のセーブを1つ作る。都市国家は置かない。読み込むユーザーMODは、保存状態を記録する既存の Bundle0 だけ。Gathering Storm が必要であり、公式DLCの設置と有効化はユーザーMODと区別して確認する。

`reliability-cycle.json` は、起動、種セーブの読込、1ターンの進行、保存、再読込、メニューへ戻る操作を行う。1ターンだけ進んだこと、MODのデータとスクリプトがあること、保存前後でターンとMODの保存状態が一致することを断言する。駒や都市を置く製品の準備は行わない。

種セーブの生成は一度だけ行う。既存の同名セーブは上書きしない。後から再検証するときは種セーブを残してcycleを実行し、読込後の版と保存状態を再確認する。別の種が必要なら試験単位で名前を変え、seedとcycle両方の参照を合わせる。各cycleではMODの観測回数が1だけ増え、最終ターンが現在ターンと一致することも確認する。

```
live_chain.exe fix/live-reliability-1971:reliability-seed.json --stop-on-failure
live_chain.exe fix/live-reliability-1971:reliability-cycle.json --reliability
```

実行器は対象ブランチからビルドする。10回の間も共有の実機ロックを使い、待っている担当へ譲る。各回の終了ではCiv6を終了し、ロックを解放する。10回は同じ試験の連続した成功であり、途中の失敗を除いて成功だけ集めない。

## 停止の証拠

実行器は `steps.jsonl` と `result.json` に加え、失敗した場合に `failure.json` を保存する。停止段階、操作名、1から始まる手順番号、エラーの種類、元のエラー全文を記録する。段階だけで製品側・基盤側の原因を断定せず、当該実機のログと照合する。

ユーザーMODと公式DLCは起動より前に設置場所を確認する。自動再起動を無効にしていても、この確認は省かない。Steamを別の場所に置いている場合は、`CIV6_DLC_DIR` で実際の `DLC` フォルダを指定する。公式DLCの有効化や独自ルールセットに対する読み込み条件は、設置確認だけでは成立しない。製品シナリオのデータ断言も必要である。

実機の合格は実際の保存ファイル、手順の結果、Civ6の終了、ロック解放で確認する。静的なRust検査の件数は、実機が通ったという根拠にしない。
