# リポジトリルール

このリポジトリで作業する人・コーディングエージェントが必ず守るルール。オーナーの指示で恒久的に決まったものを記録する。ルールを変えるときはこのファイルを更新する。

## ドキュメント

1. 仕様の正本（SSOT）は `documents/spec/ssot/` で、章・節ごとのファイルに分割している。本文中の「本書」はこのディレクトリ全体を指す。入口は索引 `documents/README.md`
2. 仕様を変えるときは SSOT の該当ファイルを更新する。仕様を別のファイルに書かない
3. 変更の経緯は Git の履歴で管理する。SSOT に更新履歴の章を作らない
4. 新しいドキュメントは `documents/` 配下に置き、`documents/README.md` の索引に追加する。例外はリポジトリの入口であるルートの `README.md` だけ
5. 使っていない目印コメント（生成スクリプト用のマーカーなど）を残さない
6. SSOT は大きいので、全体を一度に読み込まず、必要な節のファイルだけを読む

## 判断と矛盾の扱い

1. オーナーの判断が必要な事項は `documents/questions.md` に書く。決まったら SSOT の該当節へ反映し、質問リストからは削除する
2. SSOT 内の矛盾は、エージェントが独断で解消しない。オーナーに対話形式で質問し、オーナーの指示で解消する
3. オーナーが「別途議論する」とした事項は、`documents/questions.md` の「議論待ち」に背景と論点をまとめ、勝手に決めない
4. 未決事項をどの順番で議論するかはエージェントが決め、オーナーに対話形式で質問してよい。実装の着手に必要なものから優先する

## 画像

1. 新しい指導者・文明には、可能な限り自前の画像を割り当てる。対象は指導者アイコン・家紋・ロード画面・外交画面の画像。既存の画像を流用する場合は理由を記録する（PoC は `documents/poc/README.md`）
2. 画像の出典とライセンスは、`documents/poc/README.md` の「画像」と同じ形式（用途・作品・作者と年・所蔵と出典・ライセンス・元ファイル）で記録する
3. 人物画像（肖像・立ち姿・背景）の衣服や室内に家紋を描かない。生成画像は家紋を正しく描き分けられず、無関係な家紋が入るため。家紋は文明アイコンだけで示す

## Git と PR

1. オーナーが「コミットして」と言ったら、コミットに加えて push し、PR を作成する（既存の PR があれば更新する）ところまで行う
2. `main` に直接コミットしない。作業ブランチを切って PR を作る（空のリポジトリへの最初のコミットだけは例外）
3. PR を作ったらセルフレビューを行い、指摘は PR にコメントとして投稿する。指摘は価値で仕分けし、実害（誤動作・データ消失・セキュリティ・仕様違反・利用者に見える不具合）があるものを直す。修正では指摘の意図をくみ、同じ種類の問題を先回りで直す。同じ領域で2回指摘が続いたら設計から見直す。Must が出なくなり、残りの指摘の扱い（修正済み・見送りの理由・確認項目）を PR に書いたら、オーナーの確認なしでマージしてよい
4. メインの作業フォルダ（リポジトリを最初に開いたフォルダ）ではブランチを切り替えない。別ブランチの作業は `git worktree add` で作った別の作業フォルダ（例：`../civ6-banseiki-wt/<名前>`）で行い、メインのフォルダは main（または作業中のブランチ）のまま保つ

## エージェントの使い方

Python は使用しない。実行ツール、生成ツール、テストは Rust で実装する。MOD の Lua は mlua に組み込んだ Lua 5.1 で検査し、マージ前には全件を確認する（2026年10月2日、オーナー指示）。

Rustの検査は次の範囲と順序で実行する（2026年10月8日、オーナー指示）。

- 作業途中は変更したクレートと、その変更に依存するクレート・関連する結合テストを`cargo nextest run --locked -p <クレート>`で回す。公開APIの変更では利用側も確認する。保存や小修正のたびに全workspaceを繰り返さない。
- 全workspaceは、マージ前の最新ソースに対して`cargo nextest run --locked --manifest-path tools/Cargo.toml --workspace --all-targets`を1回実行する。nextestが実行しないdoctestは`cargo test --locked --manifest-path tools/Cargo.toml --workspace --doc`で確認する。Lua・シナリオ・実機の受入条件は維持し、変更に関係する検査を途中で、全件をマージ前に確認する。
- 検査の失敗は原因を直す。修正が全件結果を無効にした場合だけ全件を再実行する。同じソースのCI結果を同じ担当が重複して回さない。
- このPCではCargoの共通ゲートで生成先ごとに排他し、異なる生成先の同時件数はCPU使用率と空きメモリに応じて動的に決め、CPUが75%未満かつ空きメモリが16GiB以上なら通常は論理コア数÷4を上限に1件ずつ増枠し、CPUが90%以上または空きメモリが16GiB未満なら新しいビルドを待たせ、待機中も設定を読み直して起動時の環境変数で枠を固定せず、ビルドとnextestの並列数は実行中の件数に応じて通常最大10並列に分け、同じ生成先の検査・Clippy・ビルドは直列にまとめ、worktreeの生成先を分けてPC共通のsccacheで依存を再利用し、外部資源の検査に必要な直列指定も維持する。

1. サブエージェントには Codex CLI の GPT-6-Sol（推論強度 ultra または max）や GPT-6-Luna（max）を積極的に使う
   - 例：`codex exec -m gpt-6-sol -c model_reasoning_effort='"max"' -s workspace-write --skip-git-repo-check -C <作業フォルダ> -o <出力ファイル> - < <プロンプト>`
   - 読むだけの作業は `-s read-only`、GPT-6-Luna は `-m gpt-6-luna` にする
2. 独立した作業は複数のエージェントに分けて並列で走らせ、オーナーの待ち時間を短くする。書き込みを伴うエージェントには、1体につき1つの作業フォルダ（git worktree）を割り当てる
3. オーナーに実機での確認を頼むのは、並列の成果がそろってから1回にまとめる
4. GTO（`gto.exe`）が入っている環境では、Codex などのサブエージェントを使うたびに、どのモデルがどの作業に向いていたかの実測を GTO に送る
   - 内容：モデル、推論強度、作業の種類、所要時間、トークン数、結果の評価、向き不向きの所見。メインセッションのモデル（Claude）の所見も適宜送る
   - 送り方：`"kind": "model_fit_observation"` を含む JSON を `gto internal ingest-turn` の標準入力に渡す（`hook_event_name` に `UserPromptSubmit` を入れない）
   - 評価では、渡したコンテキストの範囲で妥当だった安全側の指摘を減点しない。依頼側の渡し方に原因がある場合は、その旨を記録する。評価を誤った場合は訂正の記録を送る
5. サブエージェントにレビューを頼むときは、実機やテストで検証済みの事実（`documents/poc/README.md` の結果、動作済みのコードなど）を必ず渡す。検証済みの事実と食い違う懸念も消させず、「要実機確認」として理由とともに出させる。確信がない懸念も遠慮なく出すよう指示する。手順とひな形は Skill `subagent-review` に従う（Skill の置き場所は PC 全体のルールで `D:\CC\Skills` に集約）

## オーナーへの依頼

1. オーナーに操作を頼むときは、やることだけをチャットに短い番号付きリストで書く。手順書ファイルへの誘導や長い説明はしない
2. オーナーに見てほしい内容（結果・表・比較・判断材料）は、ファイルを開かせずにチャット欄にそのまま出す。オーナーの作業フォルダは最新化されていないことがある
